# 現在のロボット3Dアセット構築 Guideline

## 1. 最終目標

最終成果物は単一の Blender シーンではなく、出典を追跡できる一式のデジタルアセットです。

- `robot_master.blend`：原状の階層、単位、材質、関節の原点と組立位置を保持；
- `robot_web.glb`：ウェブページ向けの軽量モデル；
- `components.json`：パーツ ID、型番、規格、説明、エビデンス、設計理由；
- 普通の組立図、分解図、および重点システムの局部図；
- カメラ視錐、LiDAR、FOV、Lift の機械ストローク、車輪ユニットの回転軸、および Arm のワークスペース補助図を選択的に表示。

参考図は初版の表現方針を定める。淡い灰色の背景、等角視点、組立図と分解図の組み合わせ、主要部品の実物の色を使い、車体、車輪、フレーム、Lift、センサ、アクチュエータを区別しやすいよう、分解時には系統間に十分な間隔を設ける。これは表示スタイルの参考であり、現在のロボットの幾何形状の元データではありません。

ウェブページ上で1つの部品をクリックした場合、3つの情報カテゴリが区別されるべきです：

1. 何であるか：ブランド、型番、数量、インターフェース、仕様；
2. どのように取付けるか：サイズ、座標、接続部品、親子関係；
3. なぜこの設計か：目的、制約、比較対象、検証結果、未解決の問題。

## 2. 事実、推定、設計説明の区分

各数値と結論には、次のいずれかの状態を付ける：

| 状態 | 意味 | 最終的な正確なモデルに使用可能か |
|---|---|---|
| `measured` | 実機上で定規、ノギス、角度計、またはキャリブレーションプロセスで得られた | 可能、日付と方法を保存する必要あり |
| `manufacturer` | メーカー図面またはデータシートに記載されている | 可能だが、取付位置は実測が必要 |
| `runtime` | 現在 ROS/制御構成で実際に使用されている | 運用状態の表示には使用可能、機械寸法を自動的に証明するものではない |
| `model-derived` | 元の CAD/STL/DAE から得られた | 可能だが、取付バージョンとの整合性を確認する必要あり |
| `photo-estimated` | 写真の比率による推定のみ | ブロックモデルのみに使用 |
| `historical` | 旧取付または廃止されたパラメータ | 現在の組立への組み込みではなく、変遷の説明のみに使用 |
| `conflict` | 2つの既存のソースが矛盾している | 片方を事実として偽装することはできない |
| `unknown` | エビデンスがない | 明らかなプレースホルダー幾何を使用 |

設計説明も「当時の実際の意思決定根拠」と「事後の合理的な説明」を区別する必要がある。例えば Pan/Tilt 角度は、テスト、FOV 計算、または設計記録によって裏付けられている場合にのみ、「local planner が前方の一定範囲を見ることができるように選択した」と記述できる。そうでない場合は、「現在の仮説であり、カメラ視錐と local costmap によるカバレッジ実験で検証する必要がある」と記述する必要がある。

## 3. 座標、単位と基準

- ROS/GLB はメートルを使用し、Blender シーン単位は Metric、Unit Scale `1.0` に設定する。
- 機械測定表はミリメートルを記録することをお勧めし、Blender にインポートする際にメートルに統一する。
- 機体全体基準は ROS を使用する：`X` 前、`Y` 左、`Z` 上。
- `base_link` は現在車軸高さにあり、地上高は約 `0.1125 m`；地面投影には `base_footprint` を使用する。
- 各運動部品のオブジェクト原点は、真の回転軸または並進軸に配置する必要があり、メッシュ幾何中心ではない。
- D435、MID360、SO101 の optical/link frame は、視覚メッシュ原点と異なる場合があり、両方を別々に保持する必要がある。

`robot.urdf.xacro` だけを実寸の根拠にしない。2026-09-20 の実測で、底部 frame の水平外形 X=`700 mm`、Y=`600 mm`、構造上面の高さ `300/515/620/1330 mm` を確認した。主構造には 4040、前方 Arm/Camera/LiDAR の垂直ブラケットには 2020 を使用する。URDF の `670 × 600 × 580 mm` の単一 box は旧運用の簡略モデルとして保持し、Blender の実構造には使用しない。

Lift 機械ストロークも最終的に `200 mm` に確定され、旧 `230 mm` Arm 可視化 span は廃止された。
主な未解決の不一致は MID360 取付 transform のみ：注釈は
`x=-0.240 m、z=0.6875 m`、運用 property は `x=+0.240 m、z=1.38 m`。
`1330 mm` は構造上の平面高さであり、MID360 取付底面原点測定の代わりにはならない。

## 4. モデリング精度の段階

### L0：構造ブロックモデル

- 正確な全体外形、軸心、主要部品位置および運動関係；
- 欠損部品は簡易 box/cylinder で表現し、目立つ `PLACEHOLDER` 材質を使用；
- 比例の確認、分解図の方向、カメラ構図、およびウェブページのインタラクションを検証する。

### L1：取付識別モデル

- 設備の外観、主要なインターフェース、取付ブラケットと締結部品の位置が識別可能；
- 車輪ユニット、モーター、ドライバー、カメラ、LiDAR、Lift、Arm、コンピュータ、電源、および制御板が明確に区別できる；
- ウェブページのハードウェア説明と分解図を十分に担う.

### L2：設計詳細モデル

- 自作部品の穴位置、曲げ加工、3Dプリント構造、配線固定点、および取付公差は信頼できる；
- 設計理由の説明、メンテナンスや分解・再組立のために使用；
- すべてのねじ山や基板部品を高ポリゴン形状で表す必要はない。

まず機体全体の L0 を完成させ、既存 CAD がある SO101/D435 を L1 に引き上げる。全体基準が固まる前に個別部品を過度に細密化しない。

## 5. Blender のシーン階層

推奨 Collection：

```text
ROBOT
├── 00_REFERENCE      写真、測定尺、URDF 補助オブジェクト；出力しない
├── 10_BASE           車体フレーム、パネル、カバー
├── 20_MOBILITY       3つの車輪ユニット、方向転換、モーター、減速機
├── 30_LIFT           直動機構、スライダ、ねじ、ブラケット、ドライバ
├── 40_ARM            SO101、腕部カメラと取付ブラケット
├── 50_PERCEPTION     MID360、D435、Pan/Tilt
├── 60_ELECTRICAL     NUC、電源、制御器、緊急停止、通信コンバータ
├── 70_CABLES         主配線とケーブルキャリア
├── 80_HELPERS        FOV、機械ストローク、軸線、包絡；必要に応じてエクスポート
└── 90_EXPLODED       分解図の制御空オブジェクトと表示注釈；実際の組み立て寸法には含まれません
```

オブジェクト名には固定の ASCII ID を使用します。例：

```text
part__perception.camera.d435
part__lift.stage.eas
part__mobility.drive.front_left
helper__perception.camera.d435.fov
anchor__lift.stage.eas.exploded
```

`components.json` の `id` は、`part__` に続く文字列と一致させます。表示名は中国語、日本語、英語で記述できますが、表示文言を変更しても ID は変えません。

## 6. 原点、階層、分解図

各インタラクティブ部品は、少なくとも以下のものを保存する：

- `assembly_transform`：実組立位置・姿勢；
- `exploded_offset`：相対組立位置・姿勢の表示オフセット；
- `parent_id`：機械組立親要素；
- `explode_group`：分解時に同期移動する組み合わせ；
- `pivot_type`：`fixed`、`revolute`、`continuous` または `prismatic`。

分解図は以下の規則に従います。

- 大システムを先に分解し、次に子コンポーネントを分解します。方向は可能な限り実取付/取り外し方向に従います。
- ハーネスは非表示にしたり、簡略化された曲線で表示したりして、分解後に視覚的なノイズを避けます。
- 電気接続関係を空間位置のみで表現せず、ウェブページでは別途 connection データで説明します。
- 通常の組立と分解図は同一のオブジェクトを使用し、2つの独立したモデルを維持しません。
- Web アニメーションは組立 transform から exploded transform へと補間し、ユーザーは一時停止、逆再生、または個々のシステムに焦点を当てることができます。

第1版では、2つのプリセットカメラビューを同時に保持することをお勧めします。`assembled_isometric` と `exploded_isometric` です。これらは同じ方位と近似的な投影比を維持し、ユーザーが各部品がどこから取り外されたか直感的に理解できるようにします。

## 7. 動作と補助可視化

以下の内容は、個別のスイッチ可能なレイヤーとして実装することをお勧めします。

- Lift：機械 `0–200 mm` ストローク、通常のソフトウェア動作範囲 `15–185 mm`、上下 keep-out；
- SO101：6 個の関節軸、現在のソフトリミットと先端作業空間近似；
- D435：RGB/Depth 視錐、Pan/Tilt 軸、neutral と測定済み scan poses；
- MID360：水平/垂直 FOV と取付傾斜角；
- 車輪ユニット：三軸 steering 回転軸、輪接地点と運動学位置；
- 安全：非常停止ボタン位置、Lift/Arm/車体可動範囲と挟み込みが生じうる箇所。

補助オブジェクトはデフォルトでは実表示には参加しません。ウェブページでは「設計説明」スイッチとして表示されます。

## 8. 設計理由記録

主要部品ごとに [DESIGN-NOTE-TEMPLATE.md](DESIGN-NOTE-TEMPLATE.md) を使って個別に記録する。少なくとも以下の点に答えてください。

- 解決すべきタスクは何ですか；
- 選択前にどのような制約がありましたか；
- なぜこの型番、位置、高さ、または角度を選択しましたか；
- 比較または放棄された代替案は何ですか；
- どのようなデータが設計の有効性を証明していますか；
- どのような内容が検証待ちの仮説ですか；
- この決定は、ナビゲーション、認識、操作、安全性、またはメンテナンスとどのような関係がありますか。

優先的に補足することを推奨します。

1. D435 Pan/Tilt の位置、軸角、neutral pose と local planner/costmap 観察範囲；
2. MID360 の高さ、傾斜角、および自己位置推定と近場回避の役割分担；
3. Lift 型番、200 mm ストローク、取付高さ、15 mm 端点保護と Arm リーチ範囲；
4. 三輪全向車体の輪位、BLV-R/XH540 選定と構造制限；
5. Lift スライダ上の SO101 の取り付け方向、高さと腕部カメラ用途。

## 9. 写真と測定取得規範

- 機体全体を同一姿勢に保ち、Lift、Pan/Tilt と Arm の位置を数値で記録します；
- 使用前、後、左、右、頂、底の6つの可能な限り直交する視点を使用します；
- カメラはできるだけ遠く、望遠を使用し、遠近法歪みを減らします；
- 各局部図には、同一平面のスケールまたはキャリブレーション板を配置します；
- 各ブラケットについて、「取付状態」と「取り外した正反面」を撮影します；
- ファイル名には、日付、部品 ID、視点、およびスケールを含めます。例：`20260921_lift.stage.eas_left_ruler.jpg`；
- 寸法記録には、測定端点を明示し、未定義の長さだけを書かないでください；
- ハーネス撮影は、起点、終点、コネクタ、および固定点を追跡できる必要があります。

## 10. Web 資産エクスポート

- 主なフォーマットは GLB/glTF 2.0 を使用します。元の STL/DAE はウェブページに直接読み込みません。
- クリック可能な部品の独立した mesh/node を保持します。同じ規格の締結部品はインスタンス化可能です。
- 視覚的なディテールにはテクスチャとマテリアル表現を使用し、不要な高ポリゴン数を避けます。
- デスクトップウェブページ向けにメインモデルを準備し、低性能機器向けに簡略化された LOD を準備します。
- エクスポート前に scale を適用しますが、関節 pivot と親子階層を破壊しないでください。
- 毎回エクスポート時に Blender ファイルバージョン、エクスポート日、GLB hash と `components.json` schema version を記録します。

推奨されるウェブインタラクション：

- hover のハイライト、click の固定選択；
- 組み立て/分解スライダー；
- システムによるフィルタリング；
- 規格、取付、設計理由、エビデンスの4つの情報タブ；
- FOV、動作範囲、接続関係の補助表示；
- `measured/manufacturer/estimated/conflict` エビデンスバッジ；
- 説明書から元の写真、マニュアル、またはキャリブレーション記録へジャンプ。

## 11. 段階別の受入基準

### Phase A：エビデンスと骨格

- P0 の寸法に未解決の不一致がないこと。
- 機体全体の L0 外形と軸中心が実機写真と一致すること。
- 主要システムすべてに固定の component ID があること。

### Phase B：組立と分解

- SO101、D435 のメッシュ再利用が完了し、MID360、車輪、Lift、車体が L1 に達していること。
- 分解順序と取り外し方向が妥当であること。
- 分解アニメーションが元の組立位置・姿勢を変更しないこと。

### Phase C：ウェブページと説明

- 各ホットスポットから対応する部品資料を開けること。
- 主要な設計説明に根拠の状態が示されること。
- 対象の Web ページで GLB が円滑に読み込まれ、モバイルでは簡略版を使用すること。
- ライセンスと第三者の帰属情報を Web ページから参照できること。

## 12. 変更記録

- `references/` は手動で書き換えません。更新が必要な場合は再コピーし、`SOURCE-MANIFEST.md` を更新してください。
- Blender に新しい部品を追加する前に、`components.json` で ID を割り当てます。
- 任意の寸法変更は、同時にソース、日付、および旧値の処理方法を記録する必要があります。
- 現在の実機と設計草案は分離されています。草案は `proposal` 状態と独立した Collection を使用します。
- 表示モデルの見た目から機械精度を主張しない。Web モデルは説明資産であり、生産 CAD を代替しません。
