🧠 Know-how · LLM · llama.cpp

LLM コマンド解析で遭遇した Prompt Cache（Longest Common Prefix）起因の空応答バグ

Intent Routing の LLM Fallback 層（llama.cpp / qwen2.5-3b-instruct-q4_k_m）で、temperature: 0 にもかかわらず 同じ入力で結果が変わるという不可解な事象に遭遇。原因調査から最終的な対処までの記録。自分用の備忘録として残す。

🤖 llama-server 🧩 qwen2.5-3b-instruct-q4_k_m 🔍 cache_prompt / LCP Cache
📚 背景

ロボットへの自然言語コマンドは Deterministic → Embedding → LLM Fallback の三層で解析している（Intent Routing 三層設計 参照）。 LLM Fallback 層は前段で解決できなかった曖昧なコマンドのみを受け持ち、ローカル LLM（llama.cpp 上の qwen2.5-3b-instruct-q4_k_m）で構造化 JSON（candidates）に変換している。

このシミュレーションではなく実運用（real）に近い形でテストを回していたときに、temperature: 0（決定的であるはず）にもかかわらず、同じプロンプトを繰り返し送ると、たまに正しい結果の代わりに空の {} が返ってくる現象を発見した。

💥 何が起きたか
Bug同一入力でも結果が不安定

プロンプトの構造は「長く固定的な command_reference ブロック」＋「末尾の短い可変 Command: ...」というもの。

You are a robot command parser.

Command reference:
- navigate ...
- stop ...
- search ...
...（長い固定説明）...

Command: Go to room A

正常時は次のような JSON が返るべきところ：

{ "candidates": [ { "skill": "navigate", "target": "room_a" } ] }

異常時はこうなる：

{}
または
{ "candidates": [] }
JSON としては合法（パースエラーにはならない）なので、普通の try/except では検知できない。「候補が0件」という意味的な異常として扱う必要がある。
なぜ？temperature = 0 でも不安定になり得る理由

temperature = 0 が保証するのは「同じ内部状態が与えられたとき、毎回同じトークンを選ぶ」ことだけ。

「その内部状態（KV Cache）自体が毎回正しく再現される」ことまでは保証しない。今回の問題はまさにここで、サンプリングではなく Prompt Cache の再利用（reuse）がおかしくなっていた。

たとえるなら、計算式（temperature=0）は毎回同じでも、電卓（llama.cpp のキャッシュ）が前回の計算の途中結果を誤って読み込んでしまう、というイメージ。
🔍 原因 — Longest Common Prefix (LCP) Cache
cache_prompt とは

LLM は毎回プロンプト全体を先頭からトークン処理する必要がある。ただし cache_prompt = true（デフォルト有効）の場合、前回のプロンプトと今回のプロンプトの「共通する先頭部分（Longest Common Prefix）」を検出し、そこまでの KV Cache を再利用して、変化した末尾部分だけを計算する。

Prompt A: 固定部分 + "Go forward"
Prompt B: 固定部分（共通） + "Turn left" → 共通部分は再計算せず再利用

今回のプロンプトは「長い固定 command_reference（約1070 token）＋短い可変 Command（約30 token）」という、まさに LCP キャッシュが最も効きやすい（＝最も酷使される）形をしていた。

何が壊れていたか（推定）

すべての詳細な内部実装までは特定できていないが、実験結果からは次のような挙動が疑われる：

  • 前回プロンプトの KV 状態の一部が正しく切り詰められていない
  • 新旧プロンプトの分岐位置（末尾の差分開始点）の処理がずれる
  • キャッシュに前回コマンドの残留状態が残る

結果として、モデル内部では実際には「固定部分 + 前回のCommand + 残留状態 + 今回のCommand」のような矛盾した文脈を見てしまい、コマンドを解釈できず候補ゼロ（{}）を返していたと考えられる。

🧪 検証（A/B テスト）
cache_prompt を切ると再現しなくなる

cache_prompt: false にして同一リクエストを6回連続実行 → 6/6 が完全に一致（byte-identical）。これでほぼ「サンプリングのランダム性」や「モデル自体の理解不足」ではなく、キャッシュ再利用に直接起因することが確認できた。

ただし代償として、毎回 ~1100 token のフル cold prompt-eval が発生し、速度が約10倍悪化。その結果、本来の timeout_sec を大量に超過するようになった。

条件正確性速度タイムアウト失敗
cache_prompt = false安定（6/6 一致）約10倍遅い61 / 126（約48%）
cache_prompt = trueまれに空結果速い約 4〜7 / 126（3〜6%）
キャッシュを切って正しさを取り戻しても、タイムアウト失敗が「元のバグよりずっと悪化」してしまい、実運用では採用できないという結論になった。
🔧 最終的な対応
Fixキャッシュは維持 ＋ 空候補時に1回だけ自動リトライ

速度を落とさず正しさも確保するため、「キャッシュは有効のまま」「異常検知時のみ1回リトライ」という方針にした。

1
通常どおりリクエスト
cache_prompt = true のまま実行。ほとんどの場合はここで完了。
2
JSON は正常でも candidates が空かを確認
LlamaCppParser.parse_candidates で「パース成功だが候補ゼロ」を意味的な異常として判定。
3
空だった場合のみ、もう1回リクエスト
リトライ時は新しい生成になり、壊れたキャッシュの続きを踏まないため、高確率で正常化する。
4
timeout_sec を 2.0 → 8.0 秒に引き上げ
LLM Fallback は「Embedding で解決できなかった全てのケース」で呼ばれる常用パスになったため、cold prompt-eval やリトライ分の余裕を確保。
キャッシュを疑って一律に「もう1回叩く」のではなく、「候補ゼロ」という意味的なシグナルをトリガーにしている点がポイント。単純な例外catchでは検知できないバグだった。
結果

リトライ導入 ＋ サーバー再起動（手動テストで汚染されたキャッシュのクリア）後の残存失敗率：

テストセット件数失敗失敗率
EN1264約 3.2%
JP11700%

残る失敗が全てキャッシュバグ由来とは限らない（タイムアウト・本当に解析不能な入力・想定外の表現なども含まれ得るため、失敗ログの分類は別途必要）。

📝 今後のための注意点
  • この不具合は「同じ入力を連続で何度も叩く」ケースで最も再現しやすかった。もし再発したら、まずは同一入力の連続実行で切り分ける。
  • より高頻度で再発する場合は、リトライ方式以外に --cache-reuse 0 や、固定プレフィックスをもっと短く／繰り返しの少ない構造にする、といった代替策も検討の余地あり。
  • 重要：空の {} を無条件に「キャッシュバグ」と決めつけない。以下は区別する必要がある：
    • 本当に該当コマンドが存在しない（正当な無マッチ）
    • キャッシュ起因の異常な空結果
    • タイムアウト
    • JSON 形式エラー
    • モデル/サーバー自体のエラー
    区別しないと、本来サポートしていない入力に対しても無意味なリトライを繰り返すことになる。
