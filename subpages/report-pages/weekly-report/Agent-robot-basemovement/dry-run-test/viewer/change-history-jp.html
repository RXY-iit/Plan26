Round 1–3 · 2026-07-06
初回 dry-run：基礎的な解析の穴を発見（F1–F12）

あらゆるコマンド種別を初めて体系的に実行し、一連の「正規表現の詰めが甘い」レベルの問題が 露呈した——アーキテクチャの問題ではなく、個々のルールが境界ケースを見落としていた。

発見修正済みF4：代名詞・曖昧語が正当な対象として扱われていた

"check it" のような指示に含まれる it は本来特定できない対象のはずが、そのまま具体的な巡視対象として受理されていた。

check it
修正前inspect_place(target=it)
修正後ask_human
発見修正済みF9：複合ターゲット名が方向語ルールに誤爆されていた

ターゲット名のクリーンアップ処理が「front を見たら方向語として切り落とす」という単純な仕組みだったため、"front door" のように front を含む本物のターゲット名が誤って "door" に削られていた。既知ターゲット名に基づくフレーズ単位のアンカー式除去に変更。

go to front door
修正前navigate_to_place(target=door)
修正後navigate_to_place(target="front door")
発見修正済みF12：アンダースコア形式が認識されない

知覚クエリの型プレフィックス用正規表現が「スペース」区切り（"object car"）しか認識せず、テンプレート集で同じく使われている「アンダースコア」形式（"object_car"）を認識していなかった——自前の warehouse シナリオの例文すら正しく解析できていなかった。

check object_car
修正前Embedding / LLM Fallback に落ちる（本来 Deterministic で直接一致すべき）
修正後search_object_here(object_query=object_car) · Deterministic
発見設計判断F6：綴り訂正——あえて修正せず、後の設計議論に持ち越し

"go to sfoa" のような綴りミスは、当時は訂正処理を一切行わないことを選択し、「設計判断が必要で、その場しのぎで直せるバグではない」と明記して保留された——この判断が最終的に決着するのは Round 5.1（下記参照）。

Round 4 · 2026-07-07
アーキテクチャ再設計：Parser と Perception の責務分担を見直し

単なる修正ではなく契約そのものの再設計：Parser はもう Perception の代わりに判断せず、 Perception の「能力」は推測ではなく実モデルのデータに基づくようになった。

アーキテクチャ変更Parser が知覚クエリに事前の「型ラベル付け」をしなくなった

以前は Parser が "green door" を先回りして "green_door" に分類しており、Perception 自身の判定ロジックと二重管理・衝突していた。現在は Parser はクリーンアップ済みの生フレーズをそのまま渡すだけで、色/物体/文字が何であるかはすべて Perception 側の一箇所で決定する。

アーキテクチャ変更「能力」は推測ではなく、実際の YOLO モデルの COCO 80クラスを参照

以前は「この単語が検出可能な物体っぽいか」をハードコードされた16個の英語接尾辞リストで判定していた。現在は現行の yolo11s.pt の重みファイルに実在するクラス名一覧を直接参照する。

check for a door / cart / sofa / chair
修正前door/cart/sofa が「物体っぽい」として検出対象にされていた（実際はモデルが認識できない）
修正後door/cart/sofa → 正しく「非対応」と判定；逆に chair は実在クラスなのに以前は漏れていたが、今は検出可能
発見修正済み"turquoise chair" 色+物体の結合バグ

新しい能力モデル導入後に露呈した新規バグ：一致しなかった色の単語と物体の単語が文字列連結時にくっついてしまい、どちらにも一致しなくなっていた。先に単語分割してから各単語を個別に照合するよう修正。

check for a turquoise chair
修正前"turquoise" + "chair" → "turquoisechair" となり、既知のどのクラスにも一致しない
修正後個別に認識：turquoise（未知の色）+ chair（実在する検出可能クラス）
アーキテクチャ変更検出しようがないクエリは、カメラスキャン全体をスキップ

以前はクエリの内容にかかわらず、必ず9姿勢のカメラスキャンを一通り行ってから検出可否を判定していた。現在は事前判定を行い、検出可能な手がかりが一切ない場合は物理動作を丸ごとスキップして、即座に人手確認が必要と報告する。

check for salfjogasf
修正前9姿勢スキャン（スキルコール18回）を最後まで完走してから NEEDS_HUMAN を報告
修正後カメラを動かさず、即座に NEEDS_HUMAN を報告
Round 5 · 2026-07-13
LLM Fallback の再設計、ローカル大規模言語モデルへの実接続

「動けばいい」では終わらせず、実際にローカルの llama.cpp サービスに接続してテスト。 同時にフォールバック層の振る舞いそのものを再設計した。

アーキテクチャ変更Deterministic / Embedding は単独で ask_human に終端できなくなった

以前は Embedding の判断が自信不足（スコアが拮抗、または閾値未満）だとそのまま「要人手確認」を返し、そこで処理が終わっていた。現在は自信を持って判断できなかった場合、必ず LLM Fallback に処理を継続して最終判断を委ねる。

アーキテクチャ変更LLM Fallback が「単一の確定回答を推測する」から「常に候補3件+キャンセル」に変更

新設計では LLM が単独で実行を確定することは二度となく、最大3件の候補案とキャンセル選択肢を提示し、人手確認に委ねる。プロンプト内の「対応コマンド一覧」も parser_templates.yaml からその場で生成する方式に変更し、陳腐化しやすい手書き文面を廃止した。

発見緩和済みllama.cpp のプロンプトキャッシュ正確性バグ

ローカルモデルへの実接続で初めて露呈：temperature=0 にもかかわらず、同一リクエストが時折壊れた空の JSON {} を返す。原因は llama.cpp の最長共通接頭辞キャッシュ再利用機構が、この「非常に長い共有プレフィックス+極端に短い可変末尾」というプロンプト構造で誤動作すること。キャッシュを無効化すれば直るが毎回のリクエストが10倍遅くなるため、「失敗時に1回だけ自動リトライ」で緩和し、残存の失敗率を 4/126（EN）・0/117（JP）まで低減。

パラメータ調整Embedding の閾値を再調整、隠れたハードコードも修正

accept_threshold を 0.94 から 0.90 へ、clarify_threshold を 0.75 から 0.78 へ変更。あわせて _is_ambiguous 内部に 0.72 という値がハードコードされたままで、設定を変えても反映されていなかった問題を発見・修正し、実際に設定値を読むようにした。

Round 5.1 · 2026-07-14
「あいまい一致は禁止」の決定を実装、実バグを修正、WARNING 階層を導入

Round 5 の実行で明らかになった問題を一つずつ修正すると同時に、「どの層に落ちるかというテストの 予想が外れただけ」なのか「システムが実際に誤った結果を出した」のかを初めて明確に区別した。

設計判断の実装F6 にようやく決着：あいまい一致はせず、Embedding/LLM に判断を委ねる

Deterministic は「既知のどのターゲットにも似ていない」入力を一律で一致拒否するようになった（編集距離などのあいまい訂正は行わない）。判定には元の部分文字列ではなく「スクリプト認識トークン化」を使用——"sofa" が "sofaa" に誤って一致するような偽陽性を避けつつ、スペースのない日本語の正当な包含関係も保持する。

go to sfoa
修正前Deterministic が navigate_to_object(target=sfoa) を黙って受理
修正後Deterministic は拒否 → Embedding が意味的類似度で自力解決（ただし綴りを "sofa" に訂正はしない——この残課題も正直に記録）
発見修正済みF16（最も深刻）：日本語の回転指示のつなぎ言葉が「90メートル移動」になっていた

"くらい"という口語的なつなぎ言葉が「90度」と「回って」の間に挟まったことで組み合わせ正規表現が一致せず、より緩い移動系正規表現に落ちてしまい、「90」を移動距離のメートル数として解釈していた。

右に90度くらい回って
修正前move_relative(direction=right, distance_m=90.0) ← 危うくロボットが90メートル移動するところだった
修正後rotate_relative(yaw_deg=-90.0)
発見修正済みF14：丁寧語・つなぎ言葉付きの視線指示が、意味不明な知覚クエリになっていた

"look up please" に含まれる余分な "please" のせいで視線方向の正規表現が一致せず、より緩い知覚検索用の正規表現に拾われ、"up please" 全体を探すべき物体として扱ってしまっていた。

look up please
修正前search_object_here(object_query="up please")
修正後look_direction(direction=front, band=upper)
発見修正済み全角単位が誤った数値に黙って解析されていた

全角文字 "ｃｍ" が半角 "cm" のみに一致する正規表現とマッチせず、デフォルトの「少しだけ」という距離に黙って後退していた——実行される距離が意図の半分になってもエラーは出なかった。Unicode の NFKC 正規化で全角/半角を統一して解決。

リフトを10ｃｍ上げてください
修正前distance_m=0.05 ← 意図は 0.10、半分しか動かない
修正後distance_m=0.1
階層の変更WARNING を新設：「テストが層を読み違えた」と「システムが本当に間違えた」を区別

あるテストケースが単に「Embedding に落ちると予想したが実際は LLM Fallback だった」（あるいはその逆）で、それ以外の項目はすべて一致している場合、今は赤い FAIL ではなく WARNING と判定する——これはテスト側の仮説の調整が必要なだけで、システムの欠陥ではない。Deterministic / Ambiguity Gate での誤りや、内容そのものが誤っている場合のみが本当の FAIL となる。

まだ解決していない、議論待ちの課題

  • Embedding のテンプレート混同："take a look at the front door" が高スコアで look_direction（本来は inspect_place）と誤判定される——現時点で real_lab マトリクス中唯一の本物の FAIL。テンプレート設計レベルの調整が必要で、単純な閾値調整では解決しない。
  • navigate_to_place / navigate_to_object を両方維持する必要があるか：下流の実行ロジックが両者を完全に同一に扱っていることをコードの証拠で確認済み——区別しているのは Parser 内部のヒューリスティック一箇所のみ。統合の有力候補だが、今回のラウンドでは着手していない。
  • 日本語の「あいまいな量の回転」分岐が存在しない："左にちょっと回転して"（左に少しだけ回転して）のように明確な角度がない場合、依然として move_relative に誤判定される——既知のバグとして正直に記録済みだが、未修正。
