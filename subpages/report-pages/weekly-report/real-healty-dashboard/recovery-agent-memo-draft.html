00

定位：两层各管什么

已确认
SCOPE — WHAT EACH LAYER OWNS

沿用你原来那张架构图的三条基本原则，Recovery Agent 不是一个新系统，而是给已有的「上层 Agent（Thinking Model，非实时）／下层 Agent（~3B，实时）」架构装上「自愈」这一项能力：

  • 下层 Recovery：秒～分钟级。roscore/driver 卡死、传感器接触不良、通信丢帧这类当场能查、当场能修的问题，检测和处置都要标准化成 Skill，不临场发挥。
  • 上层 Recovery：小时～周级。看的不是单次故障，而是「这一趟任务的日志里，有没有说明系统本身缺了什么」——你举的掉电例子就是典型：不是去修那次掉电，而是去问「为什么我们连掉电这件事都没能力发现」。

换句话说：下层解决「已知问题」，上层负责发现「未知的未知」（有没有该测但没测的东西）。这个分工也决定了下面第 3 节「怎么连」的答案——两者本来就不该用同一套节奏通信。

现状盘点：已经有的地基

CURRENT STATE — WHAT V1 ALREADY GIVES YOU

这部分是从 real-healty-dashboard-ja.html 和 health-dashboard-demo.html 的快照 JSON 里核对过的，不是我猜的：

  • 七个诊断域（H1 物理/设备/驱动、H2 ROS/平台分发、H3 指令/运动、H4 传感/感知、H5 定位、H6 导航、H7 Agent/任务），每个 item 有 OK / OBSERVED / ESTIMATED / VERIFIED / IDLE / UNKNOWN / NOT_INSTRUMENTED 等证据状态，外加三层汇总 A1–A3 和按依赖关系收口的 capabilities（如 manual_drive / auto_navigation 各自列明依赖哪些 item）。
  • 这次上线过程里已经实测修复过的 9 类真实故障：CPU 持续高温、Joy-Con 与虚拟操作抢路由、Dashboard 操作权判定错误、Modbus 指令与状态读取抢通信、ROS 延迟被误判为断线、异常恢复后状态没清干净、重复启动残留旧进程、Dashboard 直接订阅高频传感器数据、日志高频写入拖垮 CPU/磁盘。
  • 你自己已经写好的路线图 M1–M4（见下方第 6 节），以及第一个 demo 目标：Motor Driver 通信异常（检测→安全停止→重启→验证→恢复）。
为什么值得先说这段 这份现状本身就是下层 Recovery Agent 最好的原材料——七诊断域的证据状态机 + 已经踩过的 9 个坑，等于已经把「要检测什么」的清单写了大半，第 2 节直接在这个基础上补「查到之后怎么办」。

三条建议，都是为了不让下层"手滑"：

  • Recovery Skill 和 goto_pose 是同一类东西——放进架构图的 L2 Skill Layer，要有明确的前置条件和执行后校验，不是脚本堆砌。这样上层以后想"扩充能力"时，走的也是图里已经画好的「能力扩张」路径。
  • 下层只能从这张清单里选，不能自由重启/改代码——这条是你自己在报告里已经写的原则，值得在实现时真正当成硬约束（比如 Skill 注册表是只读配置，不是下层能临时生成的）。
  • 连续 N 次异常才触发，不是单次——你们已经踩过「ROS 延迟被误判成断线」这个坑，说明检测本身需要去抖动/二次确认，这条要写进每个 Skill 的触发条件里，而不是只修一次特例。
给上层的原材料 无论恢复成功还是失败，每次触发都要写结构化日志——成功的恢复本身也是信号（比如同一个 Skill 一周触发 20 次，说明该修根本原因了）。这条日志正是第 3 节上层 Agent 要读的东西，所以下面这条建议实际上要在 M2 开工时就定下来，见第 6 节的 M0.5。

CASE FILES — ONE PART FROM THE ROBOT, ONE FAILURE, ONE FIX

把上面的表格拆回一个个具体场景。每个案例都写清楚：过去没有下层 Agent 时人要怎么发现和处理，跟现在下层 Agent 怎么处理，两者的差别就是这套东西的价值所在。除了案例 4（CPU 过热）是这次上线过程里真实发生并已验证的，其余是基于已知硬件（BLVD-KRD 驱动器、Dynamixel 云台、MID-360 雷达）设计的典型场景，用来说明方法本身怎么落地。

H1 · drive_healthBLVD-KRD Modbus场景示例

案例 1 — 后轮驱动器（ID=1）Modbus 通信突然无响应

场景
任务执行中，负责后轮的驱动器（ID=1）突然停止响应 Modbus 轮询——常见原因是接线端子松动或总线瞬时电压跌落，不是驱动器真的坏了。
过去会怎样
操作员靠"车子拖着走"或直接卡住才察觉异常，然后要么现场断电重启整套电控，要么远程登录一台台驱动器排查是哪个 ID 掉线——从"感觉不对"到"确认是 ID=1 的问题"，通常要人到场花几分钟到十几分钟，而且如果只是通信抖了一下，整机重启是杀鸡用牛刀。
下层怎么处理
drive_health 连续 3 次读到 NO_RESPONSE 才触发（去抖，不因为一次抖动就动作）→ 软锁 estop 防止单侧驱动继续偏摆 → 只对 ID=1 这一路执行 restart_driver_link 重连 Modbus → 重读 present alarm/DIN3 确认恢复后解锁。
效果对比
通信抖动这类最常见的情况可以在秒级内自动闭环，操作员全程不需要在场；就算 3 次都没恢复，升级给人时也已经附上"是 ID=1、什么错误码"的结论，人不用从零排查。
H1 · dynamixel_health云台伺服场景示例

案例 2 — 相机云台伺服（ID=11）HW error，卡在固定角度

场景
云台伺服因瞬时过载或温度报 HW error=1，摄像头卡住不再跟随指令转动。
过去会怎样
这类问题最容易被误诊断方向——因为表现出来的是"感知好像没看到东西/画面固定不动"，工程师第一反应往往是去查感知算法或标定，很久之后才想到去看伺服本身的硬件状态。
下层怎么处理
dynamixel_health 一检测到 HW error 位，直接判定为硬件层问题（不进入感知排查分支）→ 清 alarm 寄存器 → 复位到安全角度 → 重读 HW error 确认清零。
效果对比
把"本该几秒钟解决、却容易被错误分类到感知问题、可能耗费半天排查方向"的情况，在报错的那一刻就正确归类并处理掉。
H4 · camera / lidar diagnostics场景示例

案例 3 — 摄像头掉帧到个位数 Hz，未崩溃但数据变差

场景
camera_color_diagnostics 从 30 Hz 掉到个位数，或 lidar_device_status 报 HMS 告警——程序不崩溃，只是数据质量在下降。
过去会怎样
因为不崩溃，这类问题通常要等下游先出问题才被注意到——比如导航突然"变笨"或 GICP 定位分数恶化，这时候已经用坏数据做过一段决策了，才会回头追溯到是传感器掉帧。
下层怎么处理
reconnect_sensor 触发 driver 重启/端口重枚举；同时因为 auto_navigation 这个 capability 本身就声明依赖该传感器数据，恢复完成前可以先把它降级为 supervised-only，阻断坏数据继续往下游传播。
效果对比
从"下游出问题才倒查回传感器"变成"传感器一掉帧就在源头处理、同时阻断传播"——这正是七诊断域里已经画好的 capabilities 依赖关系图真正该被用起来的地方。
host_resources✓ 真实已验证案例

案例 4 — CPU 持续高温（95℃ 附近，逼近 100℃ 临界）

场景
这是唯一一个已经真实发生并被人工修复过的案例：这次导入 Dashboard 时发现 CPU package 温度长期维持在 95℃ 附近，原因是高频数据订阅和逐条日志写入占满了 CPU/磁盘。人工去掉这些不必要负载后，最新实测降到 80℃ 左右。
过去会怎样
这种"温水煮青蛙"式的问题是靠人在做别的事（上线 Dashboard）时顺手发现的——如果不是正好在这个时间点有人盯着系统看，这个问题可能会一直持续到触发硬件降频保护，甚至加速硬件老化。
下层怎么接管
把这次人工诊断的动作标准化成 throttle_workload Skill：host_resources.max_temperature_c 超过预设阈值时自动降采样、暂停非关键节点、把日志降频——不再需要"正好有人顺手发现"。
效果对比
从"偶然被发现才修一次"变成"每次逼近阈值都自动处理"——这就是有没有下层 Recovery Agent 的本质区别：同一个已知问题，是变成一次性修复，还是变成常态化的保护机制。
03

上层 Recovery Agent：日志与反思循环

建议
UPPER AGENT — OFFLINE REFLECTION LOOP

你举的例子非常准："出去一趟，回来发现日志里有掉电"，上层该想的不是"这次怎么办"，而是"我们的监测里是不是该有 battery check"。这本质上是一个离线的、基于日志的差距分析（gap analysis），和 SRE 的事后复盘（postmortem）、经典自适应系统里的 MAPE-K 循环（Monitor–Analyze–Plan–Execute，围绕一份共享 Knowledge 运转）是同一类结构：下层对应 Monitor+Execute（实时），上层对应 Analyze+Plan（可以慢，但要有干净的历史数据可读）。

缺口 · 用你自己的例子验证 对照现有 7 个诊断域，确实没有"电源/电池"这个专项——H1 里的 drive_bus_voltage 是驱动器总线电压，不是电池 SOC/电量。也就是说，你的直觉是对的：现状 schema 里就是缺这一项，这不是假设，是可以直接对着现有数据核实的结论。

要让上层"能想"，日志系统需要从"广播快照"升级成"可回溯的任务记录"：

  • 任务/episode 记录：每次任务一条，含开始/结束时间、模式、途中各诊断域的状态迁移事件（什么时候从 OK 变异常、什么时候恢复——而不是存全量快照）、触发过哪些 Recovery Skill 及结果、人工介入次数、任务最终结果。
  • 复用现有证据词汇：新事件继续用 OK/OBSERVED/ESTIMATED/UNKNOWN 这套状态语言，不要为日志另造一套，上层处理起来才统一。
  • 环境量的关键拐点：温度、（未来的）电压曲线不需要全量存，抓拐点即可，但要先有"能测"这个前提——这一条本身就是第 5 节"待确认"清单里的第一条。

上层的工作节奏，建议两档，都不是实时：

  • 任务结束时触发一次「单次复盘」；
  • 每日/每周跑一次「趋势复盘」，才谈得上"哪类异常最频繁""哪类异常有解法但没检测"。

产出不是直接改配置，而是结构化提案——"建议新增 H1: battery_voltage 监测项"、"建议新增 Skill: safe_return_on_low_power"——进人工确认队列。这和你自己"权限逐步放开"的原则是一致的：上层一开始也只有建议权，没有改配置权。

上层能分析什么：4 个具体例子

建议 · 3 例基于真实 snapshot
CASE FILES — WHAT THE UPPER AGENT ACTUALLY LOOKS AT

你的理解是对的：上层的好处是"减少人的工作、让系统能自己变得更完善"。但这句话太抽象，下面 4 个例子里，后三个不是我假设的，是我对着你现在的 health-dashboard-demo.html snapshot JSON 核实过的真实数据——也就是说，就算上层 Agent 还没做出来，这些"待补的能力"今天就已经客观存在于你的系统里了，只是没人把它们汇总成一份有优先级、有证据支撑的报告。

电源 / 电池你提出的例子

例 1 — 掉电事件之后，反推"该测什么"而不是"这次怎么办"

场景
机器人出去执行一次任务，中途意外掉电，回来后你翻日志才注意到。
没有上层时
这次教训停留在你脑子里，能不能变成"下次系统里加一项电池监测"这个决定，取决于你之后有没有正好想起来、正好有空去写——大概率会被下一周更紧急的事情挤掉。
上层怎么分析
复盘这次任务日志时，发现"任务在 T 时刻异常终止，但七个诊断域里没有任何一项能解释这次终止"——按你们自己已经定的 truth_policy = unknown_is_not_ok 原则，"解释不了的异常终止"本来就该被标红，而不是被放过。据此生成提案："建议在 H1 新增 battery_voltage/battery_soc 监测项，并配套 low_power_return Skill"。
价值所在
不是"分析数据"，而是注意到数据里根本不存在能解释异常的字段——这种"发现缺失"的事，人不主动坐下来想就不会发生，但可以变成每次任务后的例行动作，而不需要占用工程师专门的时间。
H2 / H5 / H6✓ 真实存在于当前 snapshot

例 2 — Dashboard 上已经标灰、但没人系统性追踪的 3 处缺口

场景
我核对了你现在这份 snapshot，发现有 3 个诊断项目前的状态就是 NOT_INSTRUMENTED（灰色）：H2 sensor_clock_sync（"V1 では直接情報源が未実装"）、H5 localization_independent_validation（wheel odometry / FAST-LIO / GICP 三者没有交叉验证）、H6 local_costmap_output_freshness。
没有上层时
灰色不是红色，不会打断任何人，工程师日常扫一眼 dashboard 很容易一带而过——3 个灰色项目会一直"晾"在那里，直到某次因为其中一项没做而真的出了事，才会有人想起"啊我们早知道这里没测"。
上层怎么分析
把这些静态灰色标记和实际发生的事件关联起来排优先级——比如如果这周 gicp_score 有几次逼近 0.25 的告警阈值，而 localization_independent_validation 恰好就是灰色（没有交叉验证能力），上层就能把"这项该优先补"放进本周报告第一条，并附上"本周 gicp_score 逼近阈值 N 次"作为证据，而不是三个灰色项目被一视同仁地丢在待办清单最后。
价值所在
把"被动的、平时没人管的问题清单"，变成"主动的、按实际风险排过序、有数据支撑"的建议——这正是"减少人的工作"最直接的体现：本来要工程师自己把灰色标记和一周的运行数据在脑子里对上号，现在是例行报告自动做的事。
跨任务聚合方法说明（数字为举例）

例 3 — 同一个 Skill 反复触发在同一个物理部件上（预测性维护）

场景
举例说明：假设 restart_driver_link 这个 Skill 一周内被触发了 20 次，其中 15 次的对象都是 ID=2（左前轮驱动），而不是均匀分布在三个驱动器上。
没有上层时
单看任何一次日志都看不出这个规律，因为每次"最终都恢复成功了"，看起来只是个已经解决的小问题——这种跨越多次任务、需要横向统计的规律，靠人工翻日志几乎不会主动去做，除非已经严重到影响任务。
上层怎么分析
跨多次任务聚合同一 Skill 的触发对象，发现"总是同一个 ID"的模式，提出"建议物理检查 ID=2 驱动器接线/连接器，可能存在早期老化迹象"——这种横向统计对上层只是一条按天/周跑一次的聚合查询。
价值所在
把"每次都自动修好、看起来没问题"的表象，变成"其实是硬件在退化"的预警——这是自动恢复机制本身的一个副作用风险（越能自动修，问题就越不容易被人注意到），上层agent正好是补上这个风险的机制。
趋势追踪方法说明（数字为举例）

例 4 — 恢复本身在变慢，说明"已解决"的问题正在复发

场景
举例说明：throttle_workload 触发后温度回落所需的时间逐周变长（比如从"降频后 2 分钟内回落"变成"需要 10 分钟"）。
没有上层时
因为每次"最终都降下来了"，容易被当作已解决问题不再关注，直到有一天真的降不下去、触发硬件保护性停机才被重新重视。
上层怎么分析
把"恢复所需时间"本身也作为一个随时间追踪的指标，在它明显变差、但还没有真正失效前就提前报警，比如提示"散热部件可能需要检查"。
价值所在
防止一个"已经修复"的问题在没人注意的情况下慢慢演变成新的、更严重的问题——这也是只有跨越时间维度持续追踪才能看到的模式，单次事件视角天然看不到。

汇总一下"过去 vs 现在"——这几个例子共同回答的问题是：一个没有分层 Recovery Agent 的机器人系统，到底缺什么。

上下层怎么连

建议
THE OPEN QUESTION — HOW THE TWO AGENTS TALK

这是你明确说"还没想清楚"的部分。核心矛盾在于：如果做成同步 API（下层遇到搞不定的问题，实时调用上层要答案），就违反了架构图里自己写的"上层非实时、非同步"原则——下层会被上层的推理耗时拖住，分层就失去意义了。三个选项对比：

A 同步 API / RPC 调用

下层遇到未知情况直接"问"上层。响应快、逻辑直观，但会把上层的推理延迟耦合进实时链路，和"上层非实时"的原则直接冲突。不建议作为主通道，顶多作为极少数"必须立刻问人/问模型"的兜底分支。

B ROS 话题/服务异步广播

和现在 /agent/health_dashboard_state 的实现方式一致，架构风格统一。但话题更适合"状态广播"，不太适合承载"需要留痕、需要人工确认"的结构化提案。

C 共享日志/提案队列 推荐

下层只管把结构化日志写进共享存储（SQLite / JSONL 均可）；上层是完全独立、按自己节奏调度的进程，读日志、调用外部 LLM API 分析，把结论写回同一存储里的"待确认提案"队列。下层/Dashboard 只需要能读"有几条待确认提案"，不需要理解上层怎么产生的——两边通过数据管道解耦，而不是调用关系。

这个"共享状态而非直接调用"的模式不是我编的，是 2024 年一篇关于对话 Agent 分层的论文（Talker–Reasoner 架构）里明确验证过的设计：快的一层（Talker）持续跑，慢的一层（Reasoner）异步把结论写进共享内存，快的一层"读得到就用，读不到就先用旧的"，两层永远不互相阻塞。你们的"下层持续执行、上层独立思考"和这个模式几乎是同一件事，只是把"共享内存"换成更适合机器人场景、需要留痕审计的"共享日志/数据库"。

回答"是不是要用 API" 分开看两件事：上层内部调用外部 LLM（Claude/GPT 等）API 做归纳分析，这是合理甚至大概率必须的；但上层和下层之间不建议做成 API 调用关系，而是"日志进、提案出"的数据管道关系。最小实现甚至可以先是一个每天跑一次的 Python 脚本：读 SQLite → 调 LLM API → 把结果写成一份提案表或 Markdown 报告，不需要一开始就是常驻 ROS 节点或"正式 Agent"身份。等验证有用了，再考虑要不要包一层调度/UI。这个节奏也和你自己 M4 排在第 6 周才做是吻合的——不需要在 M1–M3 阶段就把上层做重。

Demo / 验证方案

建议
DEMONSTRATION STRATEGY

下层的第一个 demo：你已经选的 Motor Driver 通信异常（检测→安全停止→重启→验证→恢复）是个好选择——原因和解法都在这次上线过程里被人工验证过一次，风险边界清楚，且七诊断域里已经有完整证据链（drive_health / drive_alarm_status / drive_din3_raw）。建议把故障做成可软件复现（模拟"驱动无响应"而不必物理拔线），这样能反复回归测试，而不是靠"再等一次真的坏"。

上层的 demo 比较尴尬——长期趋势类的洞察短期内没有足够真实数据积累（M4 排到第 6 周，事件本身也低频）。两个绕开这个问题的思路：

  • 回溯验证：把这次上线过程里已经发现的 9 个真实 bug，人工整理成一批结构化历史日志（哪怕是事后补录的），喂给上层 Agent，看它能不能从这批原始记录里独立复现出你自己已经得出的结论（比如"该做日志降频""该加 CPU 温度告警"）。如果能，就是一个不需要等新数据的、有说服力的概念验证。
  • 刻意留缺口的场景：就用你举的掉电例子——故意跑一次低电量任务，只记录"任务异常中止、无法归因"（目前确实拿不到电池数据），看上层 Agent 能不能提出"应增加电源监测"。这验证的是更难的能力：发现"缺失的监控项"，而不只是分析已有数据里的规律。
