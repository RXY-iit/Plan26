🔍 導入時に発見・修復した問題（概要）

Dashboard を実機に繋いで検証する過程で、以下のような実機特有の不具合を発見し、その場で修復した。

  • CPU 温度の継続的な高温：CPU package 温度が継続的に95℃前後（crit=100℃に迫る水準）まで上昇していた問題を確認。高頻度データ購読やログ書き込みなど不要な負荷を取り除いた結果、最新の実機チェックでは80℃前後まで低下（同一条件での厳密な比較試験ではないため、長時間の熱試験は引き続き課題として残る）
  • Joy-Con の競合・カクつき：物理コントローラーと Dashboard の仮想操作が同じ経路を取り合っていた問題を解消し、操作の競合を無くした
  • Dashboard 操作権の取得不良：コントローラーの中立位置が誤って「操作中」と判定され、Dashboard 側が操作権を握れなくなる不具合を修正
  • Modbus 通信の競合：速度指令の送信と状態読み取りが同時に走り、通信エラーや反応遅延を起こしていた問題を解消し、単一の通信スケジュールに統一
  • 誤った通信エラー判定：ROS 側の処理遅延を実際の通信断線と誤認識していた判定ロジックを修正
  • 一時的なエラーが解消扱いにならない問題：通信が回復しても状態が「異常」のまま固定されてしまう不具合を修正し、正しく「復旧」を表示できるようにした
  • 重複起動時の残留プロセス：再起動時に古い制御ノードが残り、複数の指令元が競合する問題を解消
  • 高負荷データパスの見直し：Dashboard が高頻度・大容量のセンサーデータを直接購読していた設計を見直し、低頻度の要約データのみを扱う構成に変更して負荷を抑えた
  • ログの高頻度書き込みによる負荷：通信のたびに逐一書き込んでいた詳細ログを間引き・集約し、常時起動していたデバッグ用の録画ログも普段はオフにすることで、ログ処理が CPU・ディスクを圧迫していた問題を解消

🔮 今後のプラン — Recovery Agent

Health Dashboard で「見える」ようになった異常を、今後は下層 Recovery Agent が段階的に自動対処していく方向で計画中。頻度が高く原因・対処が明確でリスクの低い障害から着手し、最初からコード修正や自由な再起動はさせず、権限と対応範囲を少しずつ広げる。

段階期間内容
M1：可観測化1週目Dashboard V1 安定化、異常時のログ・状態を自動保存
M2：確定的な自動復旧2〜3週目Node 再起動・Driver 再接続などの Recovery Skill を実装
M3：タスクレベルの復旧4〜5週目異常に応じて Skill を選択し、Retry・縮退運転・人への確認を管理
M4：長期的な分析・改善6週目上層 Agent が運用記録を分析し、障害傾向をレポート化

最初の Demonstration は、これまで調査してきた Motor Driver の通信異常を対象にする予定（検出 → 安全停止 → 再起動 → 検証 → 復帰）。

Recovery Agent 構成イメージ 下層 Agent：秒〜分単位の即時対応／上層 Agent：時間〜週単位の傾向分析
