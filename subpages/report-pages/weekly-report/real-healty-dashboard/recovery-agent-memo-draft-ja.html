Recovery Agent 階層メモ

Health Dashboard V1(七診断ドメイン + 三層サマリー)がすでに稼働していることを前提に、「下層のリアルタイム復旧」と「上層の長期分析」という2つの Agent の具体的な設計案を整理し、まだ考えがまとまっていない「上下層をどう繋ぐか」という問いに答える。要確認 マークがついている箇所は、引き続き調査するか判断が必要な部分。

00

位置づけ:両層がそれぞれ何を担うか

確認済み
SCOPE — WHAT EACH LAYER OWNS

元のアーキテクチャ図にある3つの基本原則を踏襲すると、Recovery Agent は新しいシステムではなく、既存の「上層 Agent(Thinking Model、非リアルタイム)／下層 Agent(~3B、リアルタイム)」というアーキテクチャに「自己修復」という能力を追加するものである:

  • 下層 Recovery:秒〜分オーダー。roscore/driver のフリーズ、センサの接触不良、通信のフレーム落ちなど、その場で検知しその場で直せる問題を対象とし、検知と対処はその場対応ではなく Skill として標準化する。
  • 上層 Recovery:時間〜週オーダー。見るのは単発の故障ではなく、「この1回のタスクのログから、システム自体に何が欠けているかが分かるか」。掉電(電源断)の例が典型的:その掉電自体を直すのではなく、「なぜ掉電を検知する能力すら無かったのか」を問う。

つまり:下層は「既知の問題」を解決し、上層は「未知の未知」(測るべきなのに測っていないもの)を発見する役割を持つ。この役割分担が、第4節「どう繋ぐか」の答えも決めている——両者はそもそも同じテンポで通信すべきではない。

現状棚卸し:すでにある土台

確認済み
CURRENT STATE — WHAT V1 ALREADY GIVES YOU

real-healty-dashboard-ja.html と health-dashboard-demo.html のスナップショット JSON を照合して確認した内容であり、推測ではない:

  • /health_monitor ノード、read-only モード、5 Hz サンプリング・1 Hz 配信、truth_policy = unknown_is_not_ok——このポリシー自体が Recovery Agent の判断基準として非常に適している:良いと証明されていない限り良くないとみなし、「データが無い」ことを正常と誤判定しない。
  • 7つの診断ドメイン(H1 物理/デバイス/ドライバ、H2 ROS/プラットフォーム配信、H3 コマンド/モーション、H4 センサ/認識、H5 自己位置推定、H6 ナビゲーション、H7 Agent/ミッション)。各項目は OK / OBSERVED / ESTIMATED / VERIFIED / IDLE / UNKNOWN / NOT_INSTRUMENTED などの証拠状態を持ち、さらに三層サマリー A1–A3 と、依存関係で束ねられた capabilities(manual_drive / auto_navigation などがそれぞれ依存する item を明示)がある。
  • 今回の導入過程で実際に発見・修復した9種類の実機バグ:CPU の持続的高温、Joy-Con と仮想操作の経路競合、Dashboard 操作権の判定不良、Modbus の指令送信と状態読み取りの競合、ROS の遅延を通信断線と誤判定、異常復旧後に状態が正しくクリアされない、重複起動時の旧プロセス残留、Dashboard による高頻度センサーデータの直接購読、ログの高頻度書き込みによる CPU/ディスク負荷。
  • すでに作成済みのロードマップ M1–M4(下記第6節)、および最初の demo 対象:Motor Driver 通信異常(検出→安全停止→再起動→検証→復帰)。
先にこれを書く理由 この現状把握そのものが下層 Recovery Agent にとって最良の素材である——7診断ドメインの証拠ステートマシン + すでに踏んだ9つの落とし穴で、「何を検知すべきか」のリストはすでに大半が書き終わっている。第2節はこの土台の上に「検知した後どうするか」を補うだけでよい。

下層 Recovery Agent:症状 → チェック → 対処

提案
LOWER AGENT — DETERMINISTIC RUNBOOK

あなたの発想は正しい:下層に必要なのは「即座のリアルタイム検知 + 対応する操作」の一覧表であり、下層にその場で推論させることではない。以下は、すでに踏んだ9つの落とし穴を、あなたの M2/M3 の区分に沿って、そのまま Recovery Skill リストの雛形として使える表に整理したもの——すでに修復済みの落とし穴こそ、最もリスクが低く、最初に自動化すべきものである。原因と解決策がすでに一度検証されているからだ。

下層に"手が滑る"ことをさせないための3つの原則:

  • Recovery Skill は goto_pose と同じ種類のもの——アーキテクチャ図の L2 Skill Layer に置き、明確な事前条件と実行後検証を持たせる。スクリプトの寄せ集めにはしない。こうすれば上層が将来「能力を拡張」したいときも、図にすでに描かれている「能力拡張」の経路を通ることになる。
  • 下層はこのリストからしか選べず、自由に再起動したりコードを変更したりできない——これはあなた自身がレポートにすでに書いている原則であり、実装時に本当にハード制約として扱う価値がある(例:Skill レジストリは読み取り専用の設定であり、下層がその場で生成できるものではない)。
  • 連続N回の異常で初めてトリガーする、単発では動かさない——「ROS の遅延を断線と誤判定した」という落とし穴をすでに経験しているはずで、検知そのものにデバウンス/二重確認が必要だということを意味する。個別ケースを1回直すのではなく、すべての Skill のトリガー条件に組み込むべき。
上層への素材 復旧が成功しても失敗しても、トリガーのたびに構造化ログを残す——成功した復旧そのものもシグナルである(例:同じ Skill が週に20回トリガーされたら、根本原因を直すべきだというサイン)。このログこそ第3節で上層 Agent が読むものであり、したがってこの方針は M2 着手時にすでに固めておく必要がある。第6節の M0.5 を参照。

提案 · 実証済み1例
CASE FILES — ONE PART FROM THE ROBOT, ONE FAILURE, ONE FIX

上の表を、具体的なシナリオ1つ1つに分解する。各ケースには下層 Agent が無かった過去、人はどう発見しどう対処していたかと、今の下層 Agent がどう対処するかを明記する——その差分こそがこの仕組みの価値そのものである。ケース4(CPU過熱)だけは今回の導入過程で実際に発生し検証済みのものであり、それ以外は既知のハードウェア(BLVD-KRD ドライバ、Dynamixel 雲台、MID-360 LiDAR)を前提にした典型シナリオとして、手法がどう実装に落ちるかを示すためのものである。

H1 · drive_healthBLVD-KRD Modbus場面例

ケース1 — 後輪ドライバ(ID=1)の Modbus 通信が突然無応答に

場面
タスク実行中、後輪を担当するドライバ(ID=1)が Modbus のポーリングに応答しなくなる——多くは配線端子の緩みやバス電圧の瞬間的な低下が原因で、ドライバ自体が故障しているわけではない。
過去はどうか
オペレーターは「車体が引きずられる」感覚や完全な停止で異常に気づき、その場で電装系全体を再起動するか、リモートでドライバを1台ずつ調べてどの ID が落ちているかを特定する——「何かおかしい」から「ID=1 の問題だと確定する」まで、通常は人が現場で数分〜十数分かかる。しかも単なる通信の揺らぎであれば、機体全体の再起動は明らかに過剰対応である。
下層の対処
drive_health が連続3回 NO_RESPONSE を読み取って初めてトリガー(デバウンス、1回の揺らぎでは動かない)→ estop をソフトロックし片側駆動による偏向を防止 → ID=1 のみを対象に restart_driver_link で Modbus を再接続 → present alarm/DIN3 を再読み取りして復旧を確認後、ロック解除。
効果の比較
最も多い通信の揺らぎであれば秒単位で自動的に完結し、オペレーターは現場にいる必要がない。3回試みても復旧しない場合でも、人にエスカレーションする時点で「ID=1で、どのエラーコードか」という結論がすでに添えられており、人がゼロから調べ直す必要はない。
H1 · dynamixel_health雲台サーボ場面例

ケース2 — カメラ雲台サーボ(ID=11)のHWエラーで角度が固定

場面
雲台サーボが瞬間的な過負荷または温度上昇で HW error=1 を報告し、カメラが指令に追従せず角度が固定される。
過去はどうか
この種の問題は診断の方向を誤りやすい——「認識が何も見えていない/映像が固定されている」ように見えるため、エンジニアはまず認識アルゴリズムやキャリブレーションを疑い、サーボ本体のハードウェア状態を確認するまでにかなり時間がかかる。
下層の対処
dynamixel_health が HW error ビットを検知した時点でハードウェア層の問題と直接判定(認識のトラブルシュート分岐には入らない)→ アラームレジスタをクリア → 安全な角度に復帰 → HW error が 0 になったことを再確認。
効果の比較
「本来数秒で解決できるのに、認識の問題として誤分類され半日調査に費やされかねない」状況を、エラー発生の瞬間に正しく分類・処理する。
H4 · camera / lidar diagnostics場面例

ケース3 — カメラのフレームレートが一桁 Hz まで低下、クラッシュはしないがデータが劣化

場面
camera_color_diagnostics が 30 Hz から一桁 Hz まで低下、または lidar_device_status が HMS アラームを報告——プログラムはクラッシュせず、データ品質だけが低下する。
過去はどうか
クラッシュしないため、この種の問題は通常下流で先に問題が起きて初めて気づかれる——ナビゲーションが急に「おかしく」なる、GICP の定位スコアが悪化するなど。その時点ですでに劣化したデータで一定期間の判断を行っており、あとから遡ってセンサのフレーム落ちだったと分かる。
下層の対処
reconnect_sensor が driver の再起動/ポート再列挙をトリガー。同時に auto_navigation という capability がこのセンサデータに依存すると明示されているため、復旧完了前に supervised-only へ格下げし、劣化データが下流に伝播するのを遮断できる。
効果の比較
「下流で問題が起きてからセンサに遡って原因を突き止める」から「センサがフレーム落ちした時点で発生源で処理し、同時に伝播を遮断する」へ——これこそ7診断ドメインですでに描かれている capabilities の依存関係図が本来活かされるべき場所である。
host_resources✓ 実証済みの実例

ケース4 — CPU の持続的高温(95℃前後、臨界の100℃に接近)

場面
これは唯一実際に発生し人手で修復済みのケース:今回 Dashboard を導入した際、CPU package 温度が長期間95℃前後を維持していることが判明した。原因は高頻度のデータ購読と逐次ログ書き込みが CPU/ディスクを占有していたこと。不要な負荷を手作業で取り除いた結果、直近の実測では80℃前後まで低下した。
過去はどうか
この種の「ゆで蛙」的な問題は別の作業(Dashboard の導入)をしていた人がたまたま気づいたものである——もしちょうどこのタイミングで誰かがシステムを注視していなければ、ハードウェアのサーマルスロットリングが発動するまで、あるいはハードウェアの劣化が進むまで、この問題は放置され続けていた可能性がある。
下層の引き継ぎ
この人手による診断アクションを throttle_workload Skill として標準化する:host_resources.max_temperature_c が設定閾値を超えたら自動的にサンプリングを下げ、非重要ノードを停止し、ログ頻度を下げる——もう「たまたま誰かが気づく」ことに依存しない。
効果の比較
「偶然発見されて1回直す」から「閾値に近づくたびに毎回自動処理する」へ——これこそ下層 Recovery Agent の有無を分ける本質的な違いである:同じ既知の問題が、単発の修正で終わるか、常態化した保護機構になるかの差。
03

上層 Recovery Agent:ログと振り返りループ

提案
UPPER AGENT — OFFLINE REFLECTION LOOP

あなたの例は的確だ:「1回出かけて戻ってきたらログに掉電(電源断)があった」場合、上層が考えるべきは「今回どう対処するか」ではなく「自分たちの監視体制に battery check が必要ではないか」ということ。これは本質的にログに基づくオフラインのギャップ分析であり、SRE の事後振り返り(postmortem)や、古典的な自己適応システムにおける MAPE-K ループ(Monitor–Analyze–Plan–Execute、共有された Knowledge を中心に回る)と同じ構造を持つ:下層は Monitor+Execute(リアルタイム)に対応し、上層は Analyze+Plan(遅くてよいが、参照できるきれいな履歴データが必要)に対応する。

ギャップ · 自分の例で検証 既存の7診断ドメインと照らし合わせると、確かに「電源/バッテリー」専用の項目が存在しない——H1 の drive_bus_voltage はドライバのバス電圧であり、バッテリーの SOC/残量ではない。つまりあなたの直感は正しい:現状の schema にはこの項目が欠けている。これは仮説ではなく、既存データと照らして確認できる結論である。

上層が"考える"ためには、ログの仕組みを"ブロードキャストされるスナップショット"から"遡及可能なタスク記録"へ引き上げる必要がある:

  • タスク/エピソード記録:1タスクにつき1レコード。開始/終了時刻、モード、途中の各診断ドメインの状態遷移イベント(いつ OK から異常に変わり、いつ復旧したか——全量スナップショットではなく)、トリガーされた Recovery Skill とその結果、人手介入の回数、タスクの最終結果を含む。
  • 既存の証拠語彙を再利用:新しいイベントも引き続き OK/OBSERVED/ESTIMATED/UNKNOWN という状態語彙を使う。ログのために別の語彙を作らないことで、上層側の処理が統一される。
  • 環境量の重要な変曲点:温度や(将来の)電圧カーブは全量保存する必要はなく、変曲点だけ押さえればよい。ただしその前提として「測定できる」ことが必要——これ自体が第7節の「要確認」リストの最初の項目である。

上層の作業リズムは、どちらもリアルタイムではない2段構えを提案する:

  • タスク終了時に1回「単発振り返り」をトリガー。
  • 日次/週次で1回「トレンド振り返り」を実行して初めて、「どの異常が最も頻発しているか」「どの異常には解決策があるが検知が無いか」が語れる。

出力は設定を直接変更するのではなく、構造化された提案——「H1 に battery_voltage 監視項目を追加すべき」「safe_return_on_low_power という Skill を追加すべき」——として人的確認キューに入る。これはあなた自身の「権限は段階的に開放する」という原則と一致している:上層も最初は提案権のみを持ち、設定変更権は持たない。

03b

上層は実際に何を分析できるか:4つの具体例

提案 · 実データに基づく3例
CASE FILES — WHAT THE UPPER AGENT ACTUALLY LOOKS AT

あなたの理解は正しい:上層の利点は「人の作業を減らし、システム自体をより完成度の高いものにしていく」ことにある。ただこの言い方は抽象的すぎるので、以下の4つの例のうち後半の3つは仮定ではなく、現在の health-dashboard-demo.html の snapshot JSON を照合して確認した実データである——つまり上層 Agent がまだ実装されていなくても、これらの「補うべき能力」は今日この時点であなたのシステムに客観的に存在しており、ただ誰もそれを優先順位付けされた根拠つきのレポートにまとめていないだけである。

電源 / バッテリーあなたが挙げた例

例1 — 掉電(電源断)イベントの後、「今回どう対処するか」ではなく「何を測るべきか」を逆算する

場面
ロボットが1回のタスクに出て、途中で予期せず電源が落ち、戻ってきてからログを見て初めて気づく。
上層が無ければ
この教訓はあなたの頭の中に留まるだけで、「次はシステムにバッテリー監視を追加する」という決定になるかどうかは、後で偶然思い出すか、たまたま時間があるかどうかに左右される——おそらく翌週のより緊急な用件に押しのけられる可能性が高い。
上層の分析
今回のタスクログを振り返った際、「タスクが時刻Tで異常終了したが、7つの診断ドメインのどれもこの終了を説明できない」ことに気づく——すでに定めた truth_policy = unknown_is_not_ok の原則に従えば、「説明できない異常終了」自体が本来赤フラグとして扱われるべきものであり、見過ごされるべきではない。これに基づき提案を生成する:「H1 に battery_voltage/battery_soc 監視項目を追加し、あわせて low_power_return Skill を用意することを提案する」。
価値の所在
これは「データを分析する」ことではなく、異常を説明できるフィールドがデータの中にそもそも存在しないことに気づくことである——この「欠落に気づく」という作業は、人が意識的に座って考えない限り起こらないが、機械であれば毎回のタスク後の定型作業にでき、エンジニアの専用の時間を割く必要がない。
H2 / H5 / H6✓ 現行 snapshot に実在

例2 — Dashboard 上ですでにグレー表示されているが、誰も体系的に追跡していない3つのギャップ

場面
現在の snapshot を照合したところ、3つの診断項目が現状 NOT_INSTRUMENTED(グレー)であることが分かった:H2 sensor_clock_sync(「V1 では直接情報源が未実装」)、H5 localization_independent_validation(wheel odometry / FAST-LIO / GICP の3者間でクロス検証されていない)、H6 local_costmap_output_freshness。
上層が無ければ
グレーは赤ではないため誰の作業も中断させない。エンジニアが日常的に dashboard をざっと見る程度では見落とされやすく、3つのグレー項目はそのまま放置され、そのうちの1つが実際に問題を起こして初めて「そういえば以前から測っていないと分かっていた」と誰かが思い出すことになる。
上層の分析
これらの静的なグレー表示を、実際に発生したイベントと結びつけて優先順位をつける——例えば今週 gicp_score が0.25の警告閾値に何度か接近しており、かつ localization_independent_validation がちょうどグレー(クロス検証能力が無い)であれば、上層は「この項目を優先的に補うべき」を今週のレポートの一番上に置き、「今週 gicp_score が閾値にN回接近した」という根拠を添えることができる。3つのグレー項目を一律に ToDo リストの最後に並べるのではなく。
価値の所在
「受動的で普段誰も管理していない問題リスト」を「実際のリスクに基づいて優先順位付けされた、データに裏付けられた」提案に変える——これが「人の作業を減らす」ことの最も直接的な表れである:本来エンジニア自身がグレー表示と1週間分の稼働データを頭の中で突き合わせる必要があった作業が、今では定型レポートが自動で行う作業になる。
複数タスク横断集計手法の説明(数値は例)

例3 — 同じ Skill が同じ物理部品で繰り返しトリガーされる(予知保全)

場面
例として:restart_driver_link という Skill が1週間に20回トリガーされ、そのうち15回の対象がすべて ID=2(左前輪ドライバ)であり、3台のドライバに均等に分布していないと仮定する。
上層が無ければ
どの1回のログを見てもこのパターンは分からない。毎回「最終的には復旧に成功している」ため、すでに解決済みの小さな問題に見える——この複数タスクにまたがる横断的な統計が必要なパターンは、タスクに深刻な影響が出るまで人手でログを遡って能動的に探すことはまず無い。
上層の分析
複数タスクにまたがって同じ Skill のトリガー対象を集計し、「常に同じ ID」というパターンを発見して、「ID=2 ドライバの配線/コネクタを物理的に点検することを提案する、初期の劣化の兆候の可能性がある」と提案する——この横断統計は上層にとって日次/週次で走らせる集計クエリの1つに過ぎない。
価値の所在
「毎回自動的に直り、問題無いように見える」という表面的な現象を、「実はハードウェアが劣化している」という警告に変える——これは自動復旧の仕組み自体が持つ副作用リスクである(自動で直せば直せるほど、問題は人に気づかれにくくなる)。上層 Agent はまさにこのリスクを補う仕組みである。
トレンド追跡手法の説明(数値は例)

例4 — 復旧そのものが遅くなっている:「解決済み」の問題が再発しつつあるサイン

場面
例として:throttle_workload がトリガーされてから温度が下がるまでの時間が週を追うごとに長くなる(例:「降温後2分以内に下がる」から「10分かかる」へ)。
上層が無ければ
毎回「最終的には下がる」ため、すでに解決済みの問題として関心を持たれなくなりやすく、本当に下がらなくなってハードウェア保護のための強制停止が発動して初めて再び重視される。
上層の分析
「復旧に要する時間」自体を経時的に追跡する指標として扱い、明確に悪化しているが本当に機能しなくなる前の段階で早期に警告する。例えば「放熱部品の点検が必要かもしれない」と提示する。
価値の所在
「すでに修正済み」の問題が誰にも気づかれないまま新たなより深刻な問題へと変化するのを防ぐ——これも時間軸を跨いだ継続的な追跡によってのみ見えるパターンであり、単発のイベント視点では本質的に見えない。

「過去 vs 現在」のまとめ——これらの例が共通して答えているのは、階層型 Recovery Agent を持たないロボットシステムに何が欠けているのか、という問いである。

観点Recovery Agent が無い場合階層型 Recovery Agent 導入後
小さな故障の発見人が現場で異常を感じ取るか、タスク失敗後に遡って調査する下層がリアルタイムに検知・自動対処し、多くの場合人は現場にいる必要がない
復旧速度/人的コスト「何かおかしい」から問題特定まで、人が現場で数分〜十数分かかることが多いよくあるケースは秒単位で自動的に完結し、人はエスカレーション時のみ介入する
体系的な問題の発見エンジニアが"たまたま"気づくことに依存する(ケース4のCPU過熱のように)。運と能動性次第上層が一定のリズムで体系的にログを走査し、誰かが"思い出す"ことに依存しない
未カバーの監視項目グレー/未実装の項目は日常的に見落とされやすく、問題が起きて初めて重視される"説明のつかない異常"と履歴データからギャップの優先順位を逆算し、定型的な提案にする
知見の蓄積個人の経験にとどまり、人員の異動や時間の経過とともに失われる可能性がある構造化された提案と遡及可能なログとして蓄積され、チームで共有される
04

上層と下層をどう繋ぐか

提案
THE OPEN QUESTION — HOW THE TWO AGENTS TALK

これはあなたが明確に「まだ考えがまとまっていない」と言った部分。核心的な矛盾は:もし同期 API(下層が対処できない事態に遭遇したとき、リアルタイムで上層を呼び出して答えを求める)にしてしまうと、アーキテクチャ図自体に書かれている「上層は非リアルタイム・非同期」という原則に反することになる——下層が上層の推論にかかる時間に引きずられ、階層化した意味が失われる。3つの選択肢を比較する:

A 同期 API / RPC 呼び出し

下層が未知の状況に遭遇したとき、直接上層に"問い合わせる"。応答が速くロジックも直感的だが、上層の推論遅延をリアルタイムの経路に結合させてしまい、「上層は非リアルタイム」という原則と正面から矛盾する。メインの通信路としては推奨しない。せいぜい「即座に人/モデルに聞かねばならない」ごく少数のフォールバック分岐にとどめるべき。

B ROS トピック/サービスによる非同期ブロードキャスト

現在の /agent/health_dashboard_state の実装方式と一致し、アーキテクチャのスタイルとしては統一が取れる。ただしトピックは"状態のブロードキャスト"には向いているが、「痕跡を残す必要があり、人的確認が必要な」構造化された提案を運ぶのにはあまり向いていない。

C 共有ログ/提案キュー 推奨

下層は構造化ログを共有ストレージ(SQLite / JSONL のいずれでもよい)に書き込むだけ。上層は完全に独立し、自分のペースでスケジュールされるプロセスとして、ログを読み、外部 LLM API を呼び出して分析し、結論を同じストレージ内の「要確認提案」キューに書き戻す。下層/Dashboard 側は「未確認の提案が何件あるか」を読めればよく、上層がどう生成したかを理解する必要はない——両者はデータパイプラインで疎結合になり、呼び出し関係にはならない。

この"呼び出しではなく状態を共有する"というパターンは私が考えたものではなく、2024年に発表された対話 Agent の階層化に関する論文(Talker–Reasoner アーキテクチャ)で明確に検証されている設計である:速い層(Talker)は動き続け、遅い層(Reasoner)は非同期に結論を共有メモリに書き込み、速い層は「読めれば使い、読めなければ古い値を使う」。互いに相手をブロックすることはない。あなたたちの「下層が実行を継続し、上層が独立して思考する」はこのパターンとほぼ同じ発想であり、違いは"共有メモリ"を、ロボットの現場に合った、監査のために痕跡を残せる"共有ログ/データベース"に置き換えているだけである。

「API を使うべきか」への回答 2つのことを分けて考える:上層内部で外部 LLM(Claude/GPT など)の API を呼び出して帰納的な分析を行うことは、合理的でありほぼ必須とさえ言える。しかし上層と下層の間は API 呼び出しの関係にせず、「ログが入り、提案が出る」というデータパイプラインの関係にすることを推奨する。最小実装としては、1日1回動く Python スクリプトから始めてもよい:SQLite を読む → LLM API を呼ぶ → 結果を提案表や Markdown レポートとして書き出す。最初から常駐する ROS ノードや"正式な Agent"としての身分である必要はない。有効性が確認できてから、スケジューラや UI を被せるかを検討すればよい。このペースは、あなた自身が M4 を第6週に置いていることとも整合している——M1–M3 の段階で上層を重くする必要はない。

Demo / 検証方案

提案
DEMONSTRATION STRATEGY

下層の最初の demo:すでに選んでいる Motor Driver 通信異常(検出→安全停止→再起動→検証→復帰)は良い選択である——原因と解決策は今回の導入過程ですでに人手で1度検証されており、リスクの境界も明確で、7診断ドメインにはすでに完全な証拠の連鎖(drive_health / drive_alarm_status / drive_din3_raw)がある。故障をソフトウェアで再現可能にする(物理的にケーブルを抜かずに"ドライバ無応答"をシミュレートする)ことを推奨する。そうすれば「実際に壊れるのをまた待つ」のではなく、繰り返し回帰テストができる。

上層の demo はやや難しい——長期トレンド系の洞察は短期間では十分な実データが蓄積されない(M4 は第6週に予定されており、事象自体も低頻度)。この問題を回避する2つの方向性:

  • 遡及的検証:今回の導入過程ですでに発見した9つの実バグを、人手で構造化された履歴ログとして整理し(事後の追記であっても構わない)、上層 Agent に与えて、この生データからあなた自身がすでに得た結論を独立に再現できるか(例:「ログを間引くべき」「CPU 温度アラートを追加すべき」)を確認する。もしできれば、新しいデータを待つ必要のない、説得力のある概念実証になる。
  • 意図的にギャップを残したシナリオ:あなたが挙げた掉電の例を使う——意図的に低電力状態でタスクを走らせ、「タスクが異常中止し、原因を特定できない」ことだけを記録する(現状バッテリーデータは実際に取得できない)。上層 Agent が「電源監視を追加すべき」と提案できるかを見る。これはより難しい能力:「欠落している監視項目」を発見することを検証するものであり、既存データの中の規則性を分析するだけではない。
