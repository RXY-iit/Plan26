🤖 カテゴリ A — 自律移動 Navigation

自律移動 Level 1-3 — Harness 包含構造

Level は「段階」ではなく包含関係 — L3 ⊃ L2 ⊃ L1。
L1: Harness なしの単発移動操作 ／ L2: L1 を内包し Agent + Memory + Skill を追加 ／
L3: L1+L2 を内包し Self-Check・Multi-Agent・Human-in-the-loop など高階 Harness を追加する。
ROS2 + Mid360 LiDAR + Nav2 を基盤に、Harness の各層が積み重なる構造を検証する。

Level 1–3 の包含関係図
Level 3 — 高階 Harness
Level 2 — Harness 中層
Level 1 — 基盤
L1 基盤 — 単発の移動操作 Ph 0–1

LiDAR + Camera + ROS2 の直接パイプライン。Harness なしで、指示解釈から SLAM / Nav2 による単発の自律移動を実行する最小構成。

L2 Harness 中層 — Agent + Memory + Skill Ph 3–4

L1 を内包した上で Planner Agent・Episodic Memory・Skill: goto() が加わる。場所の意味理解や文脈を使って移動計画を構成する。

L3 高階 Harness — Self-Check + Multi-Agent + Human Ph 7

L1+L2 を内包した上で Self-Check・Multi-Agent・Human-in-the-loop を追加。不確実環境でも再計画し、必要時は人と協調してタスクを継続する。

💡 望ましいこと（Why）

研究室・施設内での物品配達や定期巡回は、単純だが人手依存のルーティン業務が多く残っている。

毎回ルートを手動でプログラムすることへの依存を減らし、 「行き先を言うだけで動く」「邪魔があっても自動で回避する」 基礎的な移動自動化を実現したい。

まず、センサーフュージョン・TF整合・Nav2 の安定動作という 揺るぎない基盤を確立することが全ての出発点となる。

→
🎯 このLevelで実証すること（What）

「3号室に行って」のような自然言語指示または指定座標を受け、 LiDAR SLAM によるローカライゼーション・Nav2 グローバル/ローカルプランナーを組み合わせ、 静的・動的障害物を回避しながら目標地点に到達する。

全センサー（Camera / IMU / Encoder / LiDAR）の TFツリー整合 + EKF オドメトリが正常に機能していることを確認済みで、 この Level の実装基盤は整った状態にある。

⚠ 解決したい痛点
✕固定ルートスクリプトは環境変化（人・物の移動）に対応できない
✕毎回人が介在しなければ次の行動を起こせない
✕センサー不整合によるオドメトリドリフトで位置推定が破綻する
✨ このデモの価値

「ロボットが自律的に空間を移動できる」という最も基礎的な能力を確立する。

Level 2・3 の記憶・判断能力はすべてこの安定した移動基盤の上に成立する。 FAST-LIO / ORB-SLAM3 によるマップ作成・Nav2 による自律移動が 本プロジェクト全体の技術的土台である。

室内ポイント配達ナビゲーション
音声または座標指定で部屋間を自律移動、動的障害物を回避して到達
シナリオ

「3L402 に荷物を届けて」「研究室の端まで行って」といった指示を受け、 FAST-LIO でビルドしたマップ上に自己位置を推定しながら、 廊下・ドア前・狭い通路を通って目標地点へ到達する。

移動中に人や椅子などの動的障害物が出現しても、 ローカルプランナーが即座に回避経路を生成し、停止せずに進む。 到達後、音声またはログで完了を通知する。

🗣️「3L402 に行って」 › 🤖 LLM: 目的地="3L402" → 座標変換 › 🗺️ Nav2: 最短経路を生成 › ⚡ DWB: 動的回避を継続 › ✅ 到達 → 完了通知

▸ 目的地の意味解釈：Whisper で音声をテキスト化し、LLM が部屋名/人名 → マップ座標 へ変換するセマンティックマッピングとの連携で自然な指示を処理

💡 望ましいこと（Why）

Level 1 のロボットは毎回「現在の状態だけ」で判断するため、 同じ失敗を繰り返し、経験を活かすことができない。

「朝 9 時はあの廊下が混む」「B棟の自動ドアは反応が遅い」 「田中さんはいつもエレベーター優先を希望する」といった 環境の動的特性やユーザーの習慣を記憶として蓄積することで、 判断品質を継続的に高めることができる。

過去の経験を参照するだけで、再プログラムなしに行動が賢くなっていくナビゲーションを実現したい。

→
🎯 このLevelで実証すること（What）

セマンティックマップに空間記憶・失敗記憶・ユーザー好みを重ねて記録し、 経路計画時に RAG + LLM でそれらを参照する。

「3L402 に行って」という同じ指示でも、 時間帯・過去の経路成功率・ユーザー設定に基づいて 異なる最適経路を選択できることを示す。

失敗（スタック・計画不能）の記録を次回の計画に反映し、 経験を積むほど移動品質が上がる仕組みを実証する。

⚠ 解決したい痛点
✕毎回同じ失敗ルートを試みてしまう
✕時間帯・曜日による混雑変化を考慮できない
✕ユーザーごとの好みや優先条件を記憶できない
✨ このデモの価値

「使えば使うほど賢くなるロボット」を実証する。

単純な移動能力ではなく、文脈・経験・ユーザー情報を考慮した タスク支援エージェントとしてのナビゲーションを示す点が 研究的にも産業的にも大きな差別化になる。

2-A
オフィスサービスロボット（記憶ベース）
経験・ユーザー好み・空間特性を記憶して最適な配達経路を自律選択
シナリオ

「田中さんに資料を届けて」という指示を受けたとき、ロボットは記憶DBに問い合わせる。 すると「田中さんはエレベーター優先」「東廊下は 10-11 時に混む（現在 10:30）」 「C棟のドアは自動ではなく手動」という記憶が見つかり、 これらを加味した経路（エレベーター経由・西廊下迂回）を自律生成する。

この配達が完了（または失敗）した結果も記憶に追記され、 次回はさらに精度の高い判断ができるようになる。

🗣️「田中さんに届けて」 › 🧠 RAG: 過去の配達記憶 + ユーザー好み取得 › 🤖 LLM: 記憶を考慮した経路方針を立案 › 🗺️ Nav2: 重み付きコストマップで計画 › 🚗 移動 → 📝 結果を記憶に追記
技術的なポイント
▸ 記憶タイプの分類：空間記憶（混雑・ドア状態）/ 失敗記憶（スタック地点・計画失敗経路）/ 対話記憶（ユーザーの優先順位・習慣）の3種類をそれぞれ異なるスキーマで JSON/DB に保存
▸ RAG によるコンテキスト検索：タスク説明をクエリとして ChromaDB に埋め込み検索し、関連する過去記憶を Top-K 件取得。LLM プロンプトに差し込んで経路判断を行わせる
▸ Nav2 への記憶反映：「混雑エリア」として記憶された区域は Costmap の inflation コストを一時的に引き上げ、自然にそのエリアを避けた経路を生成させる
2-B
失敗記憶による経路継続最適化
スタック・計画失敗の経験を蓄積し、同じ過ちを繰り返さない学習型ナビゲーション
シナリオ

ロボットが廊下の角でスタック（計画失敗 × 3 回連続）した経験を記録したとする。 次回、同じ目的地への移動時に記憶検索で「地点 X 付近で繰り返しスタック」が見つかると、 LLM が「この経由を避ける」か「アプローチ角度を変える」かを判断し、 代替経路を生成する。

また、「月曜午前は会議室 A 前が混む」といった時間パターン記憶も持ち、 時刻によって動的に経路重みを変化させる。

🔴 スタック検出 › 📝 失敗地点・時刻・状況を記憶DB に追記 › 🧠 次回: RAG で失敗記憶を参照 › 🤖 LLM: 回避戦略を決定 › 🗺️ コストマップにペナルティを反映
技術的なポイント
▸ 失敗の定量化：スタック時間・再計画回数・目的地到達失敗を記録。同一エリアでの連続失敗をトリガーに記憶の重みを上げる
▸ 時間パターン学習：失敗・遅延の発生時刻を統計処理し、「時間帯×場所」のリスクマトリクスを生成。Nav2 コストマッププラグインとして時刻依存の障害コストを動的注入
▸ 記憶の陳腐化対処：古い記憶には減衰係数を掛けて重みを下げ、環境変化（家具移動・改装）後に古い記憶が邪魔をしないよう時間窓を設定

💡 望ましいこと（Why）

Level 1・2 のロボットは「障害に直面したとき停止するか簡単に再計画する」だけで、 自分から状況を調べて解決しようとしない。

実際の高価値シナリオ（ドアが閉じている・エレベーターが来ない・ 目標物が見つからない）では、異常を認識し、 どのツールを使うか・人間に聞くかを自分で判断し、 メインタスクを継続推進する能力が必要になる。

望まれているのは「ナビゲーションを実行するシステム」ではなく、 「タスクを完了させる自律エージェント」である。

→
🎯 このLevelで実証すること（What）

閉ドア・混雑・認識失敗といった予期せぬ状況を検知し、 主動的に接近・視点変更・ツール呼び出し・人間への確認要求を判断する。

タスクを前提ステップに分解し、 途中で失敗が発生しても代替手段に切り替えながら最終目標まで推進する。

これにより、ナビゲーション単体ではなく タスク完了を主軸とした自律ループの実現を示す。

⚠ 解決したい痛点
✕ドアが閉じているだけで完全に停止してしまう
✕複数手順が必要なタスクを単独で遂行できない
✕状況が不確定なとき人が常に介在しなければならない
✨ このデモの価値

「論文トピック + 展示会デモ + 商用価値」の三拍子が揃う。

「人間のように問題を自分で解決しようとするロボット」という インタラクティブ自律性（Interactive Adaptive Autonomy）は、 Human-Robot Interaction 研究・産業サービスロボットの両観点で高い訴求力を持つ。

実装例
3-A
閉ドア・経路障害への主動的対処
状況を主動的に調査し、ドア種別を判断して対処策を選択・実行する
シナリオ

目的地への経路上でドアが閉じている状況を検知。 Level 1 のロボットは停止・再計画のみだが、Level 3 では主動的にドアへ接近し、 VLM でドア種別（自動 / 手動引き戸 / 手動押し戸 / 施錠）を判断する。

「自動ドア → センサー範囲に入って待機」「手動ドア → アームスキルを呼び出して開扉」「施錠ドア → 人間に解錠要請」というように、 状況に応じて適切なツール・スキルを自律選択し、 あくまでもメインタスク（部屋到達）の完了を最優先で推進する。

⚠️ パスブロック検出 › 🔍 ドアへ接近・視点変更 › 👁️ VLM: ドア種別 + 状態認識 › 🤖 LLM: 対処策選択（自動待機 / アーム / 人間要請） › ✅ ドア突破 → タスク継続
技術的なポイント
▸ 主動的視点変更：正面からでは判別困難なときに横移動 / 接近 / 頭部角度変更をロボット自身が決定し、認識品質が上がるまでアクションを繰り返す
▸ ツール呼び出しアーキテクチャ：LLM の Tool Use (Claude API) として「アーム開扉スキル」「人間通知 API」「迂回経路計算」を登録し、自律的に適切なものを呼び出す
▸ タスク継続推進：ドア処理は「前提ステップ」として管理し、解決後に即メインタスク（部屋到達）を再開。ドア前で全体が止まることはない
対処パターン
自動ドア（センサー待機） 手動ドア（アームスキル） 施錠ドア（人間要請） 通路ブロック（迂回判断）
3-B
マルチステップタスクチェーン自動化
複合指示をステップに分解し、失敗しても代替手段で最終目標まで完遂する
シナリオ

「A棟の山田さんから書類を受け取り、B棟の鈴木さんに届けて」という 複合タスクを受けると、ロボットは内部でタスクを分解する。

① A棟へ移動 → ② 山田さんを人物認識で特定 → ③ 受け取り確認 → ④ B棟へ移動 → ⑤ 鈴木さんへ手渡し、 というチェーンを自律的に計画・実行し、各ステップで失敗が起きた場合は 代替手段（別経路・代替受渡し場所・電話確認）に自動切り替えする。

🗣️ 複合指示を受信 › 🤖 LLM: ステップに分解・依存関係を整理 › 🔁 各ステップを順次実行 › ⚠️ 失敗検出 → 代替案に切り替え › ✅ 最終目標を完遂 → 全記憶に記録
技術的なポイント
▸ タスク分解と依存グラフ：LLM が複合指示を DAG（有向非循環グラフ）として分解し、前提条件が満たされたステップから優先実行。失敗ノードは代替サブグラフに置換
▸ 人物認識との統合：カメラ + VLM で廊下・部屋内の人物を特定し、指名された人物に接近・確認・インタラクションを行うサブスキルをツールとして登録
▸ 進捗の対話的報告：タスク完了・失敗・支援要求をリアルタイムでユーザーに通知（音声 / スマホ通知）し、最終完了後に実行サマリーを記憶DBに保存
応用シナリオ
書類回収・転送 複数部屋への順次配達 人物特定 + メッセージ伝達 収集 + 仕分け + 格納
